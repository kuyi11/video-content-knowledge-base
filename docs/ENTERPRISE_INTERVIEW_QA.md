# 企业知识库 RAG 面试问答准备

## 为什么 Recall@5 是 1，但 Answer point coverage 只有 0.4843？

Recall@5 只说明目标资料被召回，不能说明最终答案覆盖了所有要点。当前短板主要出现在生成阶段：故障排查、权限、API 和跨文档问题容易只回答部分步骤。下一步会使用结构化答案模板、逐项覆盖约束和 Claim 级引用，减少遗漏。

## 核心 Demo 与完整评测为什么分开？

5 条 Docker 场景是固定的可复现演示门禁，22 条评测是覆盖产品、权限、API、部署、版本、故障和无依据问题的完整质量集。前者用于展示主流程，后者用于暴露边界和优化项，两组请求不完全相同，所以分开报告。

## 当前权限能力到什么程度？

当前 Demo 实现了 `domain=enterprise` 过滤和资料边界验证，尚未接入真实用户 ACL、SSO 或行级权限。面向真实客户时需要先确认身份源、组织架构、文档权限继承和越权审计，再把 ACL 过滤放到召回之前。

## 文档更新后怎么处理？

当前通过资料内容哈希、独立索引和健康检查保证索引与资料一致。生产方案需要补充增量索引、索引 generation、灰度切换、失败回滚和更新审计。

## 如果客户有 100 万个 chunk，架构怎么变？

先确认问题量、峰值 QPS、更新频率和延迟目标，再评估分片向量库、BM25 服务、缓存、异步索引和冷热数据分层。当前 FAISS + Whoosh 适合 POC，不直接承诺支撑百万级生产负载。

## 私有化和 API 怎么选？

低敏感、低规模、需要快速验证时优先 API；数据敏感或必须内网时考虑私有化；中等规模可以采用云上或混合方案。判断必须同时看 Token、GPU、存储、并发和运维总成本。

## 4 条或 8 条 Claim 进入人工复核怎么办？

先分类为引用缺失、语义不足、资料冲突或评测标注问题，再人工确认并保留记录。没有完成复核前，不把这些 Claim 当作稳定的自动回答能力。

## 这个项目哪些是真实的，哪些是模拟的？

RAG 检索、引用校验、Output Gate、Docker 运行和评测流程是真实运行的；企业资料、客户和收益是模拟的。项目定位是企业知识库 RAG POC 和售前参考实现，不是某个客户的生产交付案例。

## 客户要求 99% 准确率，怎么回答？

先要求定义准确率的口径、问题集、风险等级、人工审核流程和统计范围，再用客户数据做基线和 PoC 验收。不能用小规模模拟数据直接承诺生产准确率。

## 你的项目和售前有什么关系？

我把业务问题拆解成数据、检索、模型、权限、安全和部署问题，使用 Demo 和评测验证方案，再把结果整理成架构、成本、边界和交付材料。这对应 AI 售前的需求澄清、方案设计、PoC 验证和技术沟通工作。
